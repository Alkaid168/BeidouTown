# 北斗镇小酒馆 MVP 设计说明

日期：2026-05-21

## 目标

小酒馆是北斗镇的公共聊天空间。MVP 目标是在当前 Next.js、Auth.js、Prisma、PostgreSQL 架构上实现一个稳定、低复杂度、适合约 10 人同时在线的小聊天室。

## 范围

本阶段实现：

- 单公共频道。
- 游客可查看最近消息。
- 登录居民可发言。
- 用户可撤回自己的消息。
- 管理员可删除任何消息。
- 消息删除或撤回后显示占位。
- 安全 Markdown 渲染。
- 短轮询刷新。
- 基础发言限流。
- 消息清理脚本。

本阶段不实现：

- 多频道。
- 私聊。
- WebSocket。
- SSE。
- 表情包上传。
- 图片消息。
- @ 提及。
- 已读状态。
- 复杂举报系统。

## 产品行为

### 查看消息

游客和登录居民都可以进入小酒馆页面并查看最近消息。消息按时间从旧到新展示，页面初次加载最近一批消息，之后通过短轮询获取新消息。

### 发送消息

只有登录居民可以发言。未登录用户在输入区看到登录提示和登录入口。

发送限制：

- 单条消息最多 500 字。
- 同一用户每 10 秒最多发送一条消息。
- 空消息、纯空白消息不可发送。

### Markdown

消息内容按安全基础版 Markdown 渲染，允许：

- 粗体。
- 斜体。
- 删除线。
- 行内代码。
- 代码块。
- 引用。
- 有序/无序列表。
- 链接。
- 换行。

禁用：

- HTML。
- 图片。
- iframe/script/style 等任何可执行或嵌入内容。

链接应以安全属性打开，避免脚本协议。

### 删除和撤回

- 用户可以撤回自己的消息。
- 管理员可以删除任何消息。
- 删除和撤回都不直接移除列表项，而是显示占位文案。
- 占位保留原消息时间和基础上下文。

### 保留策略

消息保留策略结合时间窗口和数量窗口：

- 删除 30 天以前的消息。
- 如果总消息数超过 160000 条，删除最早的超量消息。

MVP 先实现为手动脚本命令，例如 `corepack pnpm tavern:cleanup`。后续部署时可接入定时任务。

## 技术方案

### 实时策略

MVP 使用短轮询：

- 页面初次读取最近消息。
- 客户端每 2-3 秒请求新消息。
- 请求带上当前最新消息 ID 或时间戳。
- 服务端返回新增消息。

选择理由：

- 当前预计同时在线人数约 10 人。
- PostgreSQL 和 Next.js 足以承载。
- 部署简单，不需要额外实时服务。
- 后续可升级为 SSE 或 WebSocket。

### 数据模型

现有 `TavernMessage` 模型已包含：

- `id`。
- `authorId`。
- `content`。
- `isDeleted`。
- `createdAt`。
- `author`。

本阶段需要扩展模型以区分用户撤回和管理员删除：

- `deletedAt`：删除或撤回时间。
- `deletedById`：执行删除/撤回的用户。
- `deleteReason`：`WITHDRAWN` 或 `MODERATED`。

如果为了保持 MVP 简洁，也可以只用现有 `isDeleted` 加 `AdminAction`，但会无法区分撤回和管理员删除。推荐扩展字段。

### 服务边界

小酒馆模块放在 `src/features/tavern`：

- 消息读取服务。
- 消息发送服务。
- 撤回/删除服务。
- 限流逻辑。
- 清理逻辑。
- Markdown 渲染辅助。

页面放在 `src/app/tavern`。

API 放在 `src/app/api/tavern/messages`，用于短轮询读取新消息。

发送、撤回和删除可使用 server actions，保持表单和权限校验在服务端。

### 权限

- 游客：可读，不可发言，不可撤回。
- 普通居民：可读、可发言、可撤回自己的消息。
- 管理员：可读、可发言、可删除任何消息。

所有写操作都必须在服务端验证 session 和权限。

### 错误处理

- 未登录发言：提示需要登录。
- 发言过快：提示“先喝口茶，稍后再说。”
- 内容过长：提示“这句话太长了，先拆成几段吧。”
- 删除无权限：返回权限错误，不暴露内部细节。

## 测试策略

单元测试覆盖：

- 消息内容校验。
- 发言限流。
- 游��不可发送。
- 用户只能撤回自己的消息。
- 管理员可删除任意消息。
- 清理逻辑选择 30 天以前和超过 160000 条的旧消息。

集成/手动验证：

- 游客可进入小酒馆并查看消息。
- 登录用户可发送消息。
- Markdown 基础格式能渲染。
- HTML 和图片不会执行/展示。
- 用户可撤回自己的消息并看到占位。
- 管理员可删除消息并看到占位。
- 短轮询能看到新消息。

## 表情包系统后续设计备注

表情包系统不进入小酒馆 MVP，但后续建议采用共享资源加收藏映射：

- `Sticker` 表记录图片文件、上传者、尺寸、hash、创建时间。
- 图片文件只存一份。
- `UserStickerCollection` 表记录 `userId` 与 `stickerId`。
- 收藏别人的表情包时只新增映射，不复制图片。
- 上传新图片才创建新的 `Sticker` 和文件。

性能预估：

- 小规模下数据库压力可忽略。
- CPU 主要消耗在上传时的图片校验、压缩和缩略图生成。
- 存储和带宽是主要成本。
- 50 人规模可先用服务器本地磁盘，后续迁移对象存储/CDN。
