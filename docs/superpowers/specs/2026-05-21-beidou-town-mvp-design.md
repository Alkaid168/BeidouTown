# 北斗镇 MVP 设计说明

日期：2026-05-21

## 目标

北斗镇是一个面向小圈子的网页小镇。MVP 需要先验证“小镇感”和三个核心功能：小酒馆、树洞邮局、寺庙。系统预计最大用户量约 50 人，同时在线约 10 人，目标服务器为 4 核 4GB。

结论：该规模完全可实现。首要风险不是服务器性能，而是登录安全、内容管理、AI 调用费用和后续功能边界。

## 产品范围

MVP 登录后进入一个“神秘夜色”的小镇首页。首页作为区域入口，而不是普通功能列表。

核心区域：

1. 小酒馆
   - 单公共聊天室。
   - 所有登录居民可进入并发言。
   - MVP 不做私聊、多频道、用户自建房间。

2. 树洞邮局
   - 登录居民可投递心情、思考等内容。
   - 全站登录用户可见树洞列表。
   - 发布默认匿名，用户可切换为公开身份。
   - MVP 不做评论、点赞、漂流瓶或复杂举报系统。

3. 寺庙
   - 用户输入问题或心境。
   - 系统抽取塔罗牌。
   - 调用可切换 AI Provider 生成解读。
   - 保存用户自己的占卜历史，不公开展示他人的占卜记录。

4. 居民身份
   - 支持开放注册和登录。
   - 用户有统一昵称、头像和基础资料。
   - 树洞默认匿名，但可以选择公开身份。

5. 基础管理
   - 管理员可删除小酒馆消息和树洞投递。
   - 记录管理员操作。

暂不纳入 MVP：私聊、好友系统、多聊天室、评论系统、复杂举报系统、用户自建空间、App 客户端、3D 小镇、复杂游戏化系统。

## 推荐技术架构

采用 Next.js 全栈单体，内部按模块划分边界。

- 前端：Next.js、React、TypeScript。
- 后端：Next.js Route Handlers 或 Server Actions。
- 数据库：PostgreSQL。
- ORM：Prisma。
- 登录：Auth.js 或同类方案，先支持邮箱和密码。
- AI：统一 AI Provider 接口，通过环境变量选择具体模型服务。
- 部署：先保持普通 Node 服务可运行，后续可加 Docker Compose。

选择理由：

- 当前并发规模很小，不需要微服务。
- 单体项目开发快、部署简单、维护成本低。
- 内部模块化后，未来可以继续添加许多“小镇建筑”。
- 统一 API 边界可为未来 App 预留接口。

## 模块边界

1. 居民系统
   - 负责注册、登录、会话、用户资料和角色。
   - 注册先开放，后续可通过配置切换到邀请码或审核。

2. 小酒馆模块
   - 负责单公共频道消息发送、读取和管理员删除。
   - MVP 可使用短轮询或轻量实时方案，发言后本地立即显示。
   - 同时在线约 10 人时，短轮询足够承载。

3. 树洞邮局模块
   - 负责投递、列表展示、匿名/公开身份展示、管理员删除。
   - 列表按时间倒序分页加载。

4. 寺庙模块
   - 负责塔罗抽牌、用户问题记录、AI 解读生成、个人历史。
   - 不把业务代码绑定到具体 AI 供应商。

5. 管理模块
   - 负责管理员查看内容和删除操作。
   - 记录 AdminAction，便于基础审计。

6. AI Provider 模块
   - 暴露统一的 generateTarotReading 接口。
   - 支持通过环境变量切换供应商。
   - 负责输入长度限制、调用错误转换和费用风险控制。

## 核心数据模型

### User

字段包括：邮箱、密码哈希、昵称、头像、角色、创建时间。

角色：

- user：普通居民。
- admin：管理员。

后续可扩展：邀请码状态、审核状态、封禁状态。

### TavernMessage

字段包括：发送者、消息内容、创建时间、是否被管理员删除。

MVP 只有一个公共频道，不设计房间表。消息可以全部保留，前端分页加载。

### TreeholePost

字段包括：作者、内容、是否匿名、创建时间、是否被管理员删除。

展示规则：匿名时显示“匿名居民”；公开时显示居民昵称和头像。

### TarotReading

字段包括：用户、用户问题、抽到的牌、AI 解读、创建时间。

只允许用户查看自己的占卜历史。

### AdminAction

字段包括：管理员、操作类型、目标对象、操作时间。

用于记录删除聊天消息和树洞投递等基础管理行为。

## 权限规则

- 未登录用户只能访问首页、注册页和登录页。
- 登录用户可以进入小酒馆、树洞邮局、寺庙。
- 登录用户可以发送聊天消息、投递树洞、进行塔罗占卜、查看自己的占卜历史。
- 管理员可以删除小酒馆消息和树洞投递。
- 管理员操作需要记录。
- 普通用户不能查看他人的占卜历史。

## 体验设计

整体气质为“神秘夜色”：深色背景、星光、灯笼、塔罗、寺庙和小镇建筑意象。页面动效克制，不做重型 3D 或游戏引擎。

首页像小镇地图，三个入口分别通向：

- 小酒馆。
- 树洞邮局。
- 寺庙。

功能体验：

- 小酒馆：发言后立即显示，后台定期拉取新消息。
- 树洞：发布默认匿名，用户可切换为公开身份。
- 寺庙：输入问题后抽牌并生成 AI 解读；AI 失败时提示“今晚雾太重，请稍后再来”。
- 管理后台：极简列表，支持删除聊天消息和树洞内容。

## 风险控制

1. 性能
   - 50 用户、10 同时在线对 4 核 4GB 足够。
   - 避免一开始引入过重服务。

2. AI 费用
   - 限制塔罗问题长度。
   - 限制每个用户的调用频率。
   - 统一 Provider 层处理错误和超时。

3. 内容安全
   - 管理员可删除聊天和树洞内容。
   - 后续可加举报、封禁和审核。

4. 登录安全
   - 密码必须哈希存储。
   - 管理员权限必须服务端校验。
   - 注册、登录、发帖、聊天、塔罗调用都需要限流。

5. 后续扩展
   - 新功能作为独立“小镇建筑”添加。
   - 每个建筑有自己的页面、数据模型和服务模块。
   - 共享居民身份、权限、UI 布局和管理能力。

## 非目标

MVP 不追求大型社区平台能力，不做复杂社交关系，不做多端 App，不做微服务，不做高并发实时系统。重点是先稳定上线、验证氛围和核心玩法。
