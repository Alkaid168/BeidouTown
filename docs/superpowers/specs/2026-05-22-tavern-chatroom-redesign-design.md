# 酒馆聊天室视觉与交互重构设计

**目标**

把当前聊天室改造成项目的核心体验页：在保留现有 tavern 数据流、轮询、发送与撤回能力的前提下，重做视觉、布局与交互，使其更接近即时聊天软件而不是长页面表单。

## 范围

本次设计包含两部分：

1. `tavern` 页面视觉与交互重构
2. 首页北斗七星导航的 hydration mismatch 修复

不在本次范围内：

- 真实头像上传与存储
- 回复功能的数据模型变更
- 表情、贴纸、图片消息
- 管理员右键菜单的完整动作集合

## 当前问题

1. 酒馆页目前仍保留“页面整体滚动”的阅读感，输入区虽然贴底，但消息区与整体容器边界不够明确。
2. 发送区上方的说明文案冗余，破坏沉浸感。
3. 消息仍然显式展示用户名，不符合目标参考图的阅读方式。
4. 缺少头像与消息气泡关系，视觉上不像聊天软件。
5. 长文本模式当前通过直接改 `textarea` 高度实现，方向不稳定，不符合“从底部向上覆盖展开”的交互要求。
6. 暂无右键消息菜单，无法为后续“回复 / 复制 / 管理动作”扩展预留交互结构。
7. 首页北斗七星首屏服务端与客户端使用了不同的宽高比输入，导致 hydration mismatch 警告。

## 设计原则

- **消息优先**：页面的主要可滚动内容只能是消息流。
- **输入固定**：输入区是舞台前景，不参与消息滚动。
- **背景可见但不抢戏**：背景图必须融入，但文本永远优先可读。
- **默认安静，交互时显露信息**：默认只看内容，hover 再显示昵称与时间。
- **为扩展留接口，不提前实现功能**：右键菜单结构要可扩展，但本期只做撤回。

## 视觉方案

### 背景

酒馆页使用 `F:\CODES\北斗镇\聊天酒馆背景图.jpeg` 作为基础背景资源，并复制到 `public/` 供 Next.js 静态访问。

背景采用四层叠加：

1. 底层高清背景图，`cover + center`
2. 深蓝黑径向/线性渐变蒙版，压低高亮区域
3. 轻雾感与微弱模糊层，让局部高频纹理不干扰正文
4. 四周暗角，强化中部阅读区

目标效果：用户能明确感知到背景图存在，但聊天内容、头像、气泡和输入板永远比背景更醒目。

### 内容层

酒馆主体使用“中央浮层”的方式，不让内容直接贴满整个屏幕。消息区与输入区共享同一套夜色玻璃质感：

- 低透明背景
- 细描边
- 轻微 `backdrop-blur`
- hover 时出现柔和高光

整体气质比首页更室内、更安静，不再使用过强的大面积动态光扫。

## 布局方案

页面改成三段结构：

1. 顶部标题栏：`小酒馆` 与 `回到镇口`
2. 中部消息区：**唯一滚动容器**
3. 底部输入区：固定停靠，不参与滚动

具体约束：

- 整页外层使用固定高度视口布局，而不是自然文档流无限变长。
- 消息区单独 `overflow-y-auto`，滚动条只出现在消息区。
- 底部输入区始终保持在视口底部，不被消息滚动带走。
- 空消息态也要占据消息区，而不是让底部输入区上浮到奇怪位置。

## 消息样式方案

### 头像

每条消息左侧增加方形占位头像：

- 暂不接入真实头像资源
- 用纯色方框显示
- 内容为 `nickname` 的第一个字或第一个字母
- 颜色由昵称稳定映射，保证同一用户颜色固定

### 气泡

消息正文放入半透明气泡：

- 气泡主体为低透明磨砂色块
- 左侧带小尖角，形成“头像发出气泡”的关系
- 参考用户提供的截图，气泡矩形较宽、边缘柔和、不是圆角药丸
- 气泡内部优先保证多行 Markdown 可读性

### 元信息显示

默认状态：

- 不显示用户名
- 不显示发送时间
- 只显示消息正文

hover 状态：

- 显示昵称与发送时间
- 呈现为轻量浮层或贴边标签
- 不改变正文布局，不导致消息跳动

### 删除消息

删除消息仍占据消息流位置，但使用更克制的占位样式：

- 保留头像与大致布局
- 气泡内容替换为柔和、低对比的删除文案
- 不使用突兀的强边框或大块纯灰背景

## 长文本输入方案

这是本次最关键的交互之一。

### 基本行为

默认状态下，输入区是底部固定的一行/低高度输入板。

当用户点击“长文本”按钮后：

- 输入板**不通过普通文档流撑高布局**
- 而是在底部固定基座上，向上展开出一块覆盖层
- 这块覆盖层遮住上方一部分消息记录
- 消息区本身位置不变，只是视觉上被输入板覆盖一部分

### 交互约束

- 展开方向必须是“向上”，不是“向下长高”
- 收起后回到原始高度
- 展开和收起带平滑过渡
- 展开状态下，发送按钮和收起按钮仍固定在底部操作带附近，不能跑位

### 技术结构

输入区拆为两层：

1. 底部固定容器
2. 绝对定位贴底的长文本覆盖层

这样可以保证：

- 布局稳定
- 只改变覆盖层高度
- 不影响消息滚动容器的尺寸计算

## 右键菜单方案

每条消息支持右键打开上下文菜单。

### 本期功能

本期只实现：

- `撤回`：仅当 `message.canWithdraw` 为 `true` 时显示

### 结构要求

菜单必须按“可扩展动作列表”设计，而不是把撤回按钮硬编码在某一个位置。后续可以无痛增加：

- 回复
- 复制
- 管理删除
- 查看用户资料

### 交互要求

- 菜单出现在鼠标右键位置附近
- 点击空白区域关闭
- 滚动消息区关闭
- 按 `Escape` 关闭
- 同一时间只允许一个菜单打开
- hover 信息层和右键菜单层互不干扰

## 文案调整

需要删除或修改以下文案：

- 删除：`以 Alkaid16 的身份发言`
- 删除：`最多 500 字 · 每 10 秒一条 · 支持 Markdown`
- 输入框 placeholder 改为：`说点什么...`

游客态文案可保留简洁引导，但整体语气要更自然，不要像后台提示。

## 首页 hydration mismatch 修复

### 根因

[home-client.tsx](src/components/home/home-client.tsx) 当前在首屏渲染阶段直接分支：

- 服务端使用固定比例 `16 / 9`
- 客户端初次渲染使用 `window.innerWidth / window.innerHeight`

这会导致：

- 服务端输出一套星位坐标
- 客户端 hydration 首帧生成另一套坐标
- `polyline points` 与星星 `left/top` 不一致
- React 报 hydration mismatch

### 修复策略

首帧必须统一输入。

方案：

1. 组件初次渲染时，服务端与客户端都只使用同一个默认比例
2. 在 `useEffect` 挂载后读取真实窗口比例
3. 再用真实比例重新计算星位并触发平滑更新

这样能保证：

- SSR HTML 与 hydration 首帧完全一致
- 警告消失
- 用户仍能在挂载后看到适配真实屏幕的星位布局

如果需要进一步稳定动画，还可以把 `layout` 与 `frame` 的计算拆成更明确的“初始静态布局 + 挂载后动态布局”两阶段状态。

## 测试策略

### Tavern 组件测试

至少覆盖以下行为：

1. 消息区为独立滚动容器
2. 输入区固定存在于底部
3. placeholder 为 `说点什么...`
4. 顶部身份说明被删除
5. 每条消息显示首字头像
6. 默认不显示昵称文本
7. hover 后显示昵称与时间
8. 右键可打开上下文菜单
9. 可撤回消息显示 `撤回` 菜单项
10. 长文本模式切换后，输入层进入覆盖展开状态

### 首页回归测试

至少覆盖：

1. 首页已登录态仍能渲染北斗七星导航
2. 不再在首屏渲染路径中直接依赖 `window.innerWidth / innerHeight`
3. 首帧默认布局存在，挂载后可更新为真实布局

### 手动验证

1. 打开 `/tavern`，确认背景图存在但不影响文字可读性
2. 滚动时仅消息区滚动，输入区不动
3. 展开长文本后，输入板向上覆盖消息，而不是把页面撑长
4. hover 某条消息，看到昵称与时间
5. 右键自己的消息，出现撤回菜单
6. 点击空白、按 Esc、滚动消息区，菜单关闭
7. 打开 `/`，确认不再出现 hydration mismatch 红色报错按钮

## 风险与取舍

1. **hover 显示昵称** 对触屏设备不天然成立。当前桌面优先，移动端可退化为点击显示或始终弱显示，但本期先保证桌面端体验。
2. **右键菜单** 在浏览器默认上下文菜单竞争下需要阻止默认行为。本期可接受。
3. **时间格式** 若继续在 SSR 中直接用本地化字符串，有再次引发 hydration 问题的风险。实现时应统一时机，优先客户端安全展示策略。
4. **长文本覆盖层** 需要处理焦点与层级，避免遮挡发送按钮或让菜单穿透。

## 推荐实现顺序

1. 先修首页 hydration mismatch，消除开发时噪音
2. 接入 tavern 背景图与三段布局，完成“只消息区滚动”
3. 重做消息单项：头像、气泡、hover 元信息
4. 实现长文本向上覆盖展开
5. 实现右键菜单（本期只接撤回）
6. 补测试并手动验证
